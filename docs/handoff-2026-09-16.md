## 2 · What to pick up, in order

1. **D2's remaining piece.** S1's clauses do not drive the downloader: they run in Node against a
   fake `WebTransport`, and the downloader dials inside its own worker. `config.transport` — a module
   URL exporting `TransportSession` — is already the hook. What is missing is a conformance runner
   that supplies a fake transport module plus a control path into the worker; a `BroadcastChannel`
   reaches a same-origin worker. This is self-contained and could be its own row.
2. **D3**, once D2 is done. **L16 lands directly on it**: on the wire an ask already pre-empts a fill
   wholesale, so a downloader that asks mid-fill must re-issue the remainder or it silently stops
   filling. D2's `promote()` assumes the fill keeps coming. It does not.
3. **Two decisions in `cloud-queue.md` §Blocked**, neither of which an agent should take alone:
   should the gate hard-require the WASM arm, and where does a **signed** HTJ2K fixture come from.
4. **Not for cloud:** L3 and L7 need the rig over ssh; L2 is a workstation timing lane.

**The signed-image hole is the one worth escalating.** The capability row "16-bit signed with sign
extension" cannot be tested at all: no fixture exists, none can be made with the encoder in this tree
(`ojph_compress -signed true` does not survive its own `ojph_expand` at any bit depth tried), and the
package build and `lab/decode-bench/wasm` **disagree** on signed data. So `parity.mjs`'s byte-identical
result covers unsigned images only. Signed 16-bit is ordinary CT data.

## 3 · The container — what cost time to find

Everything below is verified here, not remembered. `cloud-queue.md` §Answers has the longer versions.

```bash
npm install -g playwright && export NODE_PATH="$(npm root -g)"
export CHROME_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome   # playwright pins 1243; pass it
cargo install wasm-pack                     # rustwasm.github.io is 403; the shell installer fails
rustup target add wasm32-unknown-unknown
pip install numpy                           # gen_frame_pnm.py needs it
git clone --depth 1 https://github.com/emscripten-core/emsdk.git ~/emsdk && cd ~/emsdk && ./emsdk install latest
```

* **A real study** is easy to make and the smoke study cannot decode — its frames are ASCII
  placeholders. Copy `lab/fixtures/decode_*/NNN.j2c` to `NNN.htj2k`, write a `metadata.json` with
  `frameCount`, and run `pack-study`.
* **`performance.measureUserAgentSpecificMemory()`** works headless and counts WASM heaps, plain
  `ArrayBuffer`s and `SharedArrayBuffer`s on one scale, in workers. It is delayed **10–16 s per call**
  unless you pass `--enable-blink-features=ForceEagerMeasureMemory`, which does not cost accuracy.
* **`--js-flags=--trace-gc` emits nothing** in this Chromium, to either process. Count collections
  from the `disabled-by-default-v8.gc` trace category over CDP — `lab/scripts/read_path_alloc.cjs`.
  CDP's `HeapProfiler` sampler does **not** weigh `ArrayBuffer` backing stores.
* **`client/transport-wasm/pkg/` must hold the default build.** A byob build there fails the gate:
  the conformance fake's `ReadableStream` is not a byte stream, so `getReader({mode:'byob'})` throws.
  Byob arms need a browser.
* **The source decoder exports no `Module.HEAPU8`.** Use `getEncodedBuffer(1).buffer.byteLength`,
  which measures either build identically. `dev-server.py` already sends COOP/COEP.

## 4 · Traps that produced a wrong answer here

Each of these was caught, but only by checking. They are cheap to repeat.

* **A baseline of your own making.** L17 first measured LTO at −17.8 % against a `plain` build the
  lane had itself rebuilt with a newer, slower compiler. Against the build the project pins, LTO is
  worth nothing. If you rebuild a thing, record which toolchain, and compare against the pinned one.
* **A background process moving the ground.** L15 first got a clean-looking "45 s → dead" that was a
  stray script of its own restarting the server mid-hold. Check the flags on the running process
  before and after each arm, and keep a control that is **expected** to fail — a 5 s idle timeout
  here — so a rig that cannot observe the failure is caught rather than believed.
* **A difference at the clock floor.** `performance.now()` is **5 µs** under cross-origin isolation.
  L13 nearly reported two one-tick differences as findings. Each context also has its own
  `timeOrigin`, so only `timeOrigin + now()` compares across threads.
* **`&` and `pkill`.** `cmd && VAR=x && (…) &` backgrounds the *whole chain*, so the variable is never
  set in your shell; and `pkill -f` matches your own wrapper. Kill by PID, read variables from
  absolute paths.
* **`tail -N` hiding the answer.** A truncated test log made `window-harness` look like it ran zero
  tests. It runs seven.
* **One unexplained failure, recorded rather than dressed up:** an `exact-server` test binary failed
  once while a server, a static host and a browser run were all loading the box, and has passed every
  run since including two full gates. The wire tests bind ephemeral ports, so it was not a port
  conflict, and no mechanism was established.
