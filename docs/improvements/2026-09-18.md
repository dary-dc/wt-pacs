# Improvements — fifth pass, 2026-09-18: what loopback hides

**Branch:** `claude/serene-rubin-wakfg7` · **Status:** identified, **nothing measured, nothing
coded**. Every line below is read from source (this tree, the QUIC and WebTransport crates in
`Cargo.lock`, Chromium), from specs and published results, or is arithmetic. Front door:
[`README.md`](README.md). How the list was produced, so it can be repeated:
[`../identification-sweep.md`](../identification-sweep.md).

**Brief.** Find levers for the target — a phone's browser on a 20–50 Mbit, 30–80 ms, lossy
wireless link — that no doc on any branch records, for the two goals measured apart: a fill's
time to all frames, and one frame asked on an idle session; memory counts as much as time.

**Why now.** On the workstation's browser rig a fill's page clock is about half *before the ask
leaves*, a tenth transfer and a third decode queue; one ask is 5 % transport. Every figure is
loopback, which makes round trips, slow start, loss and start-up free. The target charges for all
four.

**Target arithmetic used below:** 20 Mbit, 60 ms RTT unless stated; the QUIC library's default
initial window is 12 000 B.

## 1 · Would lose outright on a phone

| # | Finding | Evidence | Decided by |
| - | ------- | -------- | ---------- |
| **S1** | iOS stalls a WebTransport connection after 16 MB: flow control never refills (WebKit bug 319818, open 2026-08-26). A 61 MB fill would freeze at ~16 MB on every iPhone. Another project routes all WebKit to a TCP fallback for this. The UDP-fallback proposal (L21) then covers all of iOS, not ~5 % of networks; the non-TCP route is recycling the session before 16 MB and re-issuing, which the downloader already does after an ask | web | an iPhone, or Safari 26 on a Mac |
| **S2** | Chromium never migrates a WebTransport session: its client has no network-change handling, so Wi-Fi → cellular kills the session on any server shape. The client sees nothing until the *smaller* of the two idle timeouts, which the server's flag sets — the recommended 60 s doubles the measured 30 s freeze. Needs client liveness triggers (`connection` change, `online`/`offline`, `visibilitychange`, `resume`), a re-dial and a re-issue | Chromium source, by string presence | a phone; the rebind probe at a 10 s idle timeout, in a container |
| **S3** | A fill outlasts the screen lock (61 MB at 20 Mbit is 24 s) and a frozen page runs nothing. Wake lock during a fill; close on `freeze`, resume on `pageshow` | platform docs | a phone |
| **S4** | `quinn-proto` 0.11.18 fixes the MTU reset to 1200 this project saw twice and never explained: one ACK revealing four holes trips black-hole detection and pins the MTU for 60 s (upstream PR 2799). Same release: three security fixes, one a remote panic | upstream | container: bump, run the gate, grep old logs for `mtu=1200` |

## 2 · Round trips — free on loopback, never counted

| # | Finding | Size | Decided by |
| - | ------- | ---- | ---------- |
| **S5** | A cold open is **~4 RTT to first byte**; the docs say 2 (1.5). Chromium holds its CONNECT until the server's SETTINGS arrive, and the WebTransport crate sends them only after the handshake completes; then `ready`, then the ask. Two independent levers, 1 RTT each: **the ask carried in the session URL** (the path is readable before accept; today the media stream waits for the client's control stream), and **SETTINGS sent at 0.5 RTT** (a ~5-line patch to the crate, or upstream) | 240 → 120 ms on every cold open and every reconnect — and S2 makes reconnects routine | shaped-link VM; a container can build it and run conformance |
| **S6** | Serial fetches before the dial: **10** on the downloader branch, **8** on the harness's WASM arm, **7** on the workstation's early-dial path, against a minimum of 3. The downloader awaits all three decoders before it dials (`client/downloader/downloader.js:163-165`, found independently three times); today's worker path does not, so adopting it as-is adds a handshake. The static host sends 660 KB uncompressed with no cache policy (225 KB gzipped). The WASM client needs ~300 KB before it can dial, the TypeScript one ~16 KB — D2d should report time-to-dial for both | 560–800 ms at 80 ms, plus cold-connection slow start on each `.wasm` | one cell: navigation → session ready → first byte → first decoded, at 0 / 40 / 80 ms, cold and warm profile. ## 3 · The congestion window

| # | Finding | Size | Decided by |
| - | ------- | ---- | ---------- |
| **S7** | **One ask on an idle session is slow-start-bound, not link-bound**, for 50 KB–1 MB frames; 8 MB is link-bound. The window starts at 12 KB and an early-dialled idle session never grows it (`on_ack` returns while app-limited). The library **keeps a grown window forever**; Linux TCP decays an idle socket to its initial window — so a warmed session is structurally ahead of any idle TCP socket, and today we do not collect that. After a *lossy* fill the ask inherits a collapsed window and is slower than on a fresh session. A new IP resets the controller | 250 KB at 80 ms: 423 ms against 180 link-bound. Bytes the viewer needs anyway, pushed at session open: → ~260. A 32-packet paced window: → 296 | shaped-link VM, native client |
| **S8** | The library's Cubic has **no early slow-start exit** (no HyStart++; Linux TCP has it by default — here the incumbent transport is ahead). Every fill overshoots: 150–220 KB dropped in holes on the one ordered stream, a second back-off, and on deep cellular buffers seconds of queue then a mass-loss stall. It is also S4's natural trigger. The `Controller` trait is public; a wrapper needs no fork | +100–250 ms on a 1.75 s fill | VM: shallow against deep buffer, with and without jitter; Cubic, Cubic + early exit, BBR |
| **S9** | A radio blink of ≥ 0.5 s is declared persistent congestion: window to 2 packets, ~0.9 s of regrowth for a link that did not change. TCP does the same today | ~0.9 s per outage | VM, scripted blackouts |
| **S10** | The first probe timeout, before any RTT sample, is 999 ms (`initial_rtt` 333 ms) | ~4 % of cold opens at 1 % loss stall a second | VM, cold-connect P95 / P99 |
| **S11** | Two leads for the controller lane: the pacer ignores BBR's pacing rate, and BBR enters ProbeRtt on the first ACK after ≥ 10 s idle (`exiting_quiescence` is never set) | unknown | that lane's source review |

**A correction owed.** "Initial window: leave at the default, ≤ 7 %" never tested S7's cell. Its
source is an instrument check on a rig whose own README says not to quote it, averaging many asks
on one session, where every arm converges after a frame or two; the "window restarts after idle"
explanation it leans on is refuted by the library's source. Correct it in place where it is stated.

## 4 · When the link, not the decoder, sets the pace

| # | Finding | Decided by |
| - | ------- | ---------- |
| **S12** | One decoder covers a 20 Mbit link on a phone for every fixture (arithmetic: cine needs 0.34 of a desktop decoder at 2.5 MB/s, ≤ 0.86 at a phone's 2.5×). A pool that grows while the decode queue stays non-empty and shrinks when idle saves two workers and two heaps. Sizing from `hardwareConcurrency` (client-shape M2) sizes for loopback. This narrows the pool; it is not decoder width | container under a rate limit and CPU throttle, then a phone |
| **S13** | The engine's compiled-code cache can never engage for the decoder: it is instantiated from a buffer, the glue evaluated as text (which a CSP without `unsafe-eval` also blocks). Every visit's first frames run baseline code — published at 18–70 % slower — while optimising jobs compete with the fill. D6's warm-up decode would not tier up (per-function budget, no on-stack replacement): D6 should report cold HTTP cache and warm code cache apart. May be the unexplained once-per-session ~12 ms on the BYOB module | container, persistent profile, two visits |
| **S14** | A stray fourth copy per frame in the decoder worker (`client/downloader/decoder.js:59` copies a view that is already a `Uint8Array`) — 26 % of per-frame allocation; D4's copy table omits it. Hypothesis: GC pauses are part of a fill's 10.0 against 6.6 ms per decode. Rides with D5 | container, D4's GC counter |
| **S15** | The downloader's compressed-frame queue is bounded only by the study (61 MB, or GBs). Letting the reader pause pushes back through QUIC flow control — no server cap — and deletes M3's fill-window protocol, whose stated reason (a waiter per frame) D3 already removed | container, the stalling fake decoder |

## 5 · Bytes and fixtures

**Rejected by the owner, 2026-09-18, and recorded so it is not re-proposed.** The work is judged on
one comparison: the same frames, the same lossless encoding, the same measurement as the baseline,
and a final image that is bit-exact. S17's lossy options and S19's grey split change the content;
S16 and S18 move no figure that comparison reports. S16 had already run (queue row 31) and should
not have been queued; row 40 is held. A lever may change when bytes arrive or what is shown first
— never what the frame finally is.

| # | Finding | Decided by |
| - | ------- | ---------- |
| **S16** | **The decode bench's fixtures are 8.7× too large for cine** (428 KB synthetic against 49 KB real; grey 1.25:1 against CT's ~2.1:1). At 0.5 bpp block decoding is a minor share and the inverse transform, colour and copy-out dominate. This gates the decode timings, the share D5 assigns the range pass, D7, and L19's "a quarter of the bytes" (likely higher on low-entropy content). **Run before D5 and D7** | container: two realistic fixture modes, re-run `decode_bench` and `prefix_levels` |
| **S17** | Already-lossy sources (ultrasound cine is often lossy JPEG) inflate an estimated 2–4× under a lossless transcode — unverified — and fill time on the target scales with it. Every fixture's source is uncompressed, so no campaign sees it. Options: pass the source through to the platform's decoder (not bit-exact across decoders), or an irreversible encode (fidelity is the owner's call) | a census of source transfer syntaxes in a real archive; then a container sweep |
| **S18** | TLM markers and per-resolution tile-parts at ingest: ~126 B per frame, resolution boundaries become a header read (no decoder on the server), and DICOM's RPCL transfer syntax **requires** TLM — today's streams are valid only under the plain one. Zero effect on a fill today; the cost of deciding late is re-ingesting an archive | container sweep: bytes, both decoders byte-exact, boundaries match L19's |
| **S19** | Smaller: a mostly-grey RGB frame pays 18 % of its bytes and 2.1× decode for chroma; code-block geometry (32×128); the source build's wrapper zero-fills and then clamps per sample — the range pass belongs in that loop | container, on S16's fixtures |

## 7 · Looked at and dropped — do not re-look

TLS resumption and address-validation tokens (Chromium's WebTransport client has no session cache);
Retry (never sent); transferable streams (add a hop, chunks cross a port); posting one compiled
module to the workers (the engine already shares one compile per process); BYOB into the WASM heap
(not detachable); GPU decode (nothing runs in a browser); fewer decompositions (≤ 0.5 %); header
dedup, precincts, PLT, quality layers; JPEG-XL / JPEG-LS; `sendOrder`, `getStats`,
`congestionControl`, `anticipatedConcurrentIncoming*` (all absent in Chrome — the TypeScript
client's `"low-latency"` hint does nothing there, and the ask window's `auto` mode has no
`getStats` input); a SharedWorker holding the session (no shared memory); spurious-loss undo
(only on the library's unreleased main); datagram, crypto and stream-window settings (limits, not
allocations). **Dropped by decision, 2026-09-18:** one endpoint per core — load does not even out,
a collision costs a third of throughput, a UDP front makes that permanent, a rebind kills 3 in 4,
and in a browser it measured a tie. The transport branch parked it the same day. **Corrected
2026-09-19:** this file repeated that branch's finding that its per-byte work loses 29–38 %
throughput without the per-core endpoints; the branch retracted it (`6e2e113`: the revert had left
the binary single-threaded). It now claims, natively, less CPU per ask in every cell and one
regression at depth 1, large frames, four sessions — and, by its own measurement, a tie in a
browser. Claims until the workstation reproduces them; its server is not merged before that.
