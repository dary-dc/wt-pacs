**Brief.** An isolated attempt to cut PACS serve latency on the CPU / copy / allocation /

## The CPU thesis is abandoned

Read first: `claude/serene-rubin-wakfg7` (commits through `c8e2773`). That branch already
ran the CPU / copy / encode levers on both this class of VM and a real workstation. Do not
repeat them.

| What they tried | What they measured | Why not again |
| --- | --- | --- |
| App-level alloc / parse / JSON / locks | callgrind: `exact_server::*` < 0.3 % of instructions; `serde_json` 0.06 % | not on the critical path |
| Zero-copy send, coalesced header | already the only send path on `main` (L1 chunked write) | withdrawn there as a duplicate |
| `lto = "fat"`, `codegen-units = 1` | CPU/frame −4 to −8 %; workstation e2e **indistinguishable** from `main` (native); fill **+7.5 %** under Chromium (fadvise on a warm study) | CPU moved; e2e latency did not |
| `aws-lc-rs` vs `ring` on VAES | +3–5 % CPU at 32 KB, tie at 250 KB, +10–18 % RSS | tie or loss |
| `max_udp_payload_size` past 1472 | Chromium advertises 1472; 0 datagrams above that | closed for browser clients |
| `posix_fadvise(WILLNEED)` on fill | cold 250 kB misses 60 % → ~1 % on an evicted 8 GB study; **warm / browser a cost** | not on `main`; do not re-land |

On the workstation they then compared `main`, that branch, and a reference server, native
drivers, 61 MB cold, eviction verified (residency 1.0 → 0 → 1.0). Every median gap was
narrower than one arm's run-to-run range. `locate` and `prepare` were ~0; **99 %+ of
`serve_us` was `send`**; all three arms sat in 225–284 MB/s — the shared QUIC cost, not
memcpy or parse.

That is the falsification. A further memcpy, UTF/JSON, or per-frame alloc cut cannot move
e2e latency on a host where the app is already < 0.3 % of instructions and the send path
is the ceiling. This pass does not touch those sites.

## Pivot: the first ask sat behind the media uni

Product clients (TypeScript, WASM, `window-harness`) open the control bidi and send the
first ask without waiting for the server's media uni. The server used to:

1. accept the control bidi
2. **await** `open_uni` through ready
3. only then start the ask reader

The first ask could already be in the QUIC buffer at step 2. The first frame's read could
not start until the uni handshake finished.

**Shipped (pending the A/B below):** `FrameOut::begin` starts the shared uni at session
accept. `accept_bi` and the ask reader run without waiting for it. The first
`send_frame` awaits the uni, so the first read overlaps the handshake. Per-frame mode is
unchanged. Not a memcpy cut.

The native `server_ab` client still waits for `accept_uni` before asking, so its per-ask
p50 does not include this wait. Session `wall_ns` on a one-ask cell does. Both are quoted.

Not tried, and not this pass: mmap (ADR rejects blocking the executor), streaming a frame
before it is whole (the reader returns one frame; `READ_WINDOW` chunks the write), writing
the 8-byte head before the read (that would re-serialise the uni wait in front of the
read).
