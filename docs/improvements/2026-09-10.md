# Improvements — 2026-09-10: CPU hot path abandoned

**Branch:** `cursor/latency-cpu-hotpath-093d` · **Status:** both the assigned CPU thesis and
the first-byte-wait pivot are **ties on this host**. No product change lands. Front door:
[`README.md`](README.md).

**Brief.** An isolated attempt to cut PACS serve latency on the CPU / copy / allocation /
parse / encode path. The previous report already closed that path on a real computer. This
pass does not retry it. The pivot — a wait that delayed the first ask and the first read —
was built, interleaved, and dropped.

**Tier.** T2-local: the cloud runner this branch was measured on, localhost, no shaping.
Relative comparisons only. This box was sharing cores with other agents; one-ask wall on
the same binary spanned 1.4–12 ms. **The host is past a clean latency measurement.**
Nothing below is a workstation number.

---

## The CPU thesis is abandoned

Read first: `claude/serene-rubin-wakfg7` (commits through `c8e2773`). That branch already
ran the CPU / copy / encode levers on both this class of VM and a real workstation. Do not
repeat them.

| What they tried | What they measured | Why not again |
| --- | --- | --- |
| App-level alloc / parse / JSON / locks | callgrind: `exact_server::*` < 0.3 % of instructions; `serde_json` 0.06 % | not on the critical path |
| Zero-copy send, coalesced header | already the only send path on `main` (L1 chunked write) | withdrawn there as a duplicate |
| `lto = "fat"`, `codegen-units = 1` | CPU/frame −4 to −8 %; workstation e2e **indistinguishable** from `main` (native); fill **+7.5 %** under Chromium (fadvise on a warm study) | CPU moved; e2e latency did not |
| `aws-lc-rs` vs `ring` on VAES | +3–5 % CPU at 32 KB, tie at 250 KB, +10–18 % RSS | tie or loss |
| `max_udp_payload_size` past 1472 | Chromium advertises 1472; 0 datagrams above that | closed for browser clients |
| `posix_fadvise(WILLNEED)` on fill | cold 250 kB misses 60 % → ~1 % on an evicted 8 GB study; **warm / browser a cost** | not on `main`; do not re-land |

On the workstation they then compared `main`, that branch, and a reference server, native
drivers, 61 MB cold, eviction verified (residency 1.0 → 0 → 1.0). Every median gap was
narrower than one arm's run-to-run range. `locate` and `prepare` were ~0; **99 %+ of
`serve_us` was `send`**; all three arms sat in 225–284 MB/s — the shared QUIC cost, not
memcpy or parse.

That is the falsification. A further memcpy, UTF/JSON, or per-frame alloc cut cannot move
e2e latency on a host where the app is already < 0.3 % of instructions and the send path
is the ceiling. This pass does not touch those sites.

## Pivot: the first ask sat behind the media uni — **tie, not taken**

Product clients (TypeScript, WASM, `window-harness`) open the control bidi and send the
first ask without waiting for the server's media uni. The server still:

1. accept the control bidi
2. **await** `open_uni` through ready
3. only then start the ask reader

The first ask can already be in the QUIC buffer at step 2. A branch-local `FrameOut::begin`
started the uni at session accept so the first read could overlap the handshake. Per-frame
mode was unchanged. Not a memcpy cut.

`lab/disk-access-bench` `server_ab`, 12 interleaved repeats, arm order reversed every
repeat, `lab/fixtures/frames_32k` (80 × 32 KiB), shared mode, warm — no eviction. Both
servers stayed up. Pairing is per repeat.

The native `server_ab` client waits for `accept_uni` before asking, so per-ask p50 does
not include the uni wait. Session `wall_ns` on a one-ask cell does.

### One-ask wall (the wait the change can see)

| cell | repeats | main wall p10 | branch wall p10 | paired median | signs branch worse | verdict |
| ---- | ------: | ------------: | --------------: | ------------: | -----------------: | ------- |
| on-demand, depth 1, 1 ask | 12 | 2.0 ms | 1.5 ms | **+5.6 %** | 6/12 | indistinguishable |

Same-binary wall on `main` alone: 1.4–7.3 ms. The p10 gap is inside one arm's range.
Signs are a fair coin.

### Per-ask p50 (uni wait is outside this clock)

| cell | repeats | main p50 | branch p50 | paired median | signs branch worse | verdict |
| ---- | ------: | -------: | ---------: | ------------: | -----------------: | ------- |
| on-demand, depth 1, 1 ask | 12 | 191 µs | 182 µs | **+2.9 %** | 6/12 | indistinguishable |
| on-demand, depth 1, 64 asks | 12 | 72 µs | 72 µs | **+3.8 %** | 7/12 | indistinguishable |
| fill, 64 frames | 12 | 4.0 µs | 5.7 µs | **+13.6 %** | 7/12 | indistinguishable |

Fill p50 is inter-arrival after the first envelope and sits on a few microseconds; the
delta is quantised, not a regression. Latency only — wall of the 64-frame cells is the
same work divided by depth and is not quoted.

**Reading.** Opening the uni earlier does not move e2e latency on this host. `open_uni`
was already measured at 0.0 ms in [`adr-client-window-depth.md`](../adr-client-window-depth.md);
the handshake is not the thing the client is waiting for once the ask clock starts, and
even the one-ask wall (which includes connect + bidi + uni) does not separate the arms.
The change is dropped. `main` still serves an ask that arrives before the client accepts
the media uni — that order is now pinned by
`an_ask_before_the_media_uni_is_accepted_is_still_served`.

Not tried, and not this pass: mmap (ADR rejects blocking the executor), streaming a frame
before it is whole (the reader returns one frame; `READ_WINDOW` chunks the write), writing
the 8-byte head before the read (that would put the uni wait back in front of the read).
