# Improvements — third pass, 2026-09-10: the release profile lands

**Branch:** `claude/serene-rubin-wakfg7` · **Status:** one product change landed (P1), one
measured tie recorded (the crypto provider), the remaining server levers placed with what each
needs. Front door: [`README.md`](README.md); ledger §8: [`ledger.md`](ledger.md).

**Brief.** Reduce server latency and the resources it uses. Both lanes are on `main` now, so
"the lanes should agree" no longer holds P1 back. It was re-measured on this runner against the
code that ships (the ask-reader loop, the two readers), interleaved, before it was landed.

**Tier.** T2-local: one 4 vCPU VM (Xeon @ 2.10 GHz with AES-NI, VAES and AVX-512), 16 GB,
Linux 6.18, `cargo 1.94.1`, localhost, no shaping. Relative comparisons only.

**Method.** One saturate harness per cell (`window-harness --mode saturate --depth 4
--read-bps 0`, 4 s dwell), four cells (32 KB / 250 KB × shared / per-frame), four telemetry
server builds, **four repeats with the arm order reversed every repeat**. Server CPU is
user + system over the whole run divided by frames served (`serve_us.count`); `send_us` is the
server's own stage clock; VmHWM is the process peak. Deltas are paired per repeat against `base`,
with sign counts. Throughput is shown only to prove nothing regressed — this rig is
transfer-bound and it moves inside its own noise.

**Reading.**

- **Server CPU per frame −4 to −8 % in every cell**, 4/4 repeats each, no overlap. The same
  size as the 2026-09-08 measurement (−5 to −8 %) on a different baseline: the QUIC and
  crypto crates gain from cross-crate inlining that the app code (< 0.3 % of instructions)
  cannot.
- **`send_us` p95 −3 to −9 %**; p50 −5 % in the 250 KB per-frame cell. At 32 KB a hit is a
  probe and a copy, so p50 is 2–4 µs and its delta is quantised to the microsecond — not quoted.
- **Memory:** VmHWM −3 to −7 % in three cells, +1.7 % (3/4) in one. Not a claim either way;
  the binary is 26 % smaller (7 074 280 → 5 221 744 B, default build) and that is where the
  small saving comes from.
- **The baseline moved since 2026-09-08** (32 KB shared: 274 → 148 µs per frame, `send_us`
  p50 35 → 2 µs). That is the disk lane's inline hit path landing on `main`, not this change.
  The two compound.
- **Cost.** A release rebuild of the server after touching one file: 10 s → 39 s (default
  build), 75 s with `telemetry`, on this box. Every workspace binary is built with it, the wasm
  crate included: P2's table already has that crate under this exact profile (−2.5 % gzip,
  `init()` unchanged). `opt-level = "s"` for the wasm package — the other −10 % of P2 — is a
  client call and is not taken here.

## Crypto provider · `aws-lc-rs` against `ring` on VAES hardware — **tie or loss, not taken**

The transport lane measured the provider swap at ≤ 3 % or nil. The open question was whether a
CPU with VAES / AVX-512 would change that, since that is what `aws-lc-rs`'s AES-GCM is
vectorised for. Same run, two more arms:

| cell | `awslc` vs `base`, CPU / frame | VmHWM | `lto-awslc` vs `base`, CPU / frame | VmHWM |
| ---- | -----------------------------: | ----: | ---------------------------------: | ----: |
| 32 KB / shared | **+3.2 % (4/4)** | +18.4 % (4/4) | −2.1 % (4/4) | +14.7 % |
| 32 KB / per-frame | **+5.4 % (4/4)** | +18.0 % (4/4) | −3.0 % (4/4) | +14.7 % |
| 250 KB / shared | −0.5 % (2/4) | +13.1 % (4/4) | −6.1 % (4/4) | +14.9 % |
| 250 KB / per-frame | −1.4 % (3/4) | +18.2 % (4/4) | −4.1 % (4/4) | +10.2 % |

**Reading.** On 32 KB frames `aws-lc-rs` costs 3–5 % more CPU per frame, 4/4; on 250 KB it
ties. With LTO it is behind `lto` alone in three cells and level in the fourth. Every cell
carries +10 to +18 % peak RSS and a binary 2.2 MB larger. `send_us` is flat except one cell
(250 KB per-frame p50 −8.7 %, 3/4; p95 flat). `crypto-ring` stays the default; the
`crypto-aws-lc-rs` feature stays as the way to re-measure on other hardware.

## What would move the server further, and what each needs

None of these is a code change this pass can make on its own evidence. Recorded so the profile
does not read as the whole plan.

| lever | measured worth | what it needs | where |
| ----- | -------------- | ------------- | ----- |
| `max_udp_payload_size` 1472 → 4000 B | −35 % CPU, +55 % throughput — the largest effect measured anywhere | the peer must advertise the same ceiling, and the peer is a browser; a decision on which clients matter | [`disk-access/adr.md` §8](../disk-access/adr.md) |
| P0 — ring vs pool on the production target | a tie deletes ~800 lines and 2 fds per session that misses; a margin keeps the ring | the target: instance, volume class, container image | [`disk-access/NEXT.md`](../disk-access/NEXT.md) #1 |
| park on the ring fd, drop the eventfd | 1 fd per session instead of 2, measured tie | after P0 keeps the ring | [`NEXT.md`](../disk-access/NEXT.md) #7 |
| `--send-window-bytes` under slow clients | ≈ 1.4 MB per session at 1 MB against the 10 MB default (16 slow sessions) | a BDP number per deployment; exposed, default unchanged | [telemetry review §4.4](../telemetry/analysis-scale-and-serving-path-2026-09-06.md) |
| bounded process-private frame cache | −20 % CPU at a 0.92 hit rate, lab only | a real ask trace to size it | [`disk-access/adr.md` §5](../disk-access/adr.md) |
| S2 — several endpoints on `SO_REUSEPORT` sockets | unmeasured; the receive side is one core today | a box where 16+ clients are not the bottleneck | [`telemetry/followups-later.md` §6](../telemetry/followups-later.md) |
| `read_ahead_kb` and study layout | miss rate moved 2–15× by that knob | per target, tuning not code | [`NEXT.md`](../disk-access/NEXT.md) #6 |
| D5 — one WARN per refused frame | a log line per ask from a misbehaving client | a product call on levels | [§D5](2026-09-08.md#d5--log-hygiene-normal-closes-and-refusals-are-warn-lines) |

### Checked and left alone

- **The app code.** Two small allocations per frame (`upcoming`, `ahead`) and one FoD body
  against 140–900 µs of QUIC work per frame; the 2026-09-06 callgrind put `exact_server::*`
  under 0.3 % of instructions and nothing since has added a per-frame term.
- **Threads.** Tokio's worker count and blocking-pool cap are defaults; the tile ring and the
  fill reader bound OS threads by design (ADR §7), so a cap is not a lever.
- **`tracing`.** quinn's per-packet events are interest-cached off under the default filter;
  they did not appear in the instruction profile.

## How to re-run

The driver is the 2026-09-06 one on the archive tag, with the harness flag it predates
(`--ipv4` became `--bind 127.0.0.1`). This pass also reversed the arm order every repeat; the
sign counts above say order did not matter.

```bash
bash server/scripts/gen_dev_cert.sh && FRAMES=80 bash lab/scripts/gen_tf_fixtures.sh
cargo build --release -p window-harness
# the arms: the profile as it was, the tree's profile, and aws-lc-rs on each
CARGO_PROFILE_RELEASE_LTO=false CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16 \
  cargo build --release -p exact-server --features telemetry --target-dir /tmp/base
cargo build --release -p exact-server --features telemetry && cp target/release/exact-server /tmp/lto
cargo build --release -p exact-server --no-default-features --features uring,crypto-aws-lc-rs,telemetry \
  && cp target/release/exact-server /tmp/lto-awslc
git show archive/improvements-lab-2026-09:lab/improvements/scripts/sendpath_ab_bench.sh > /tmp/ab.sh
sed -i 's/--ipv4/--bind 127.0.0.1/' /tmp/ab.sh
REPEATS=4 bash /tmp/ab.sh out.jsonl base /tmp/base/release/exact-server lto /tmp/lto
```
