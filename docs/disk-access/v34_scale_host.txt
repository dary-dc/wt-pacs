--- stride calibration (SCALE-RUN.md step 2) ---
The doc's recipe reads the *block device* read_ahead_kb (128 here). On btrfs that is not
what governs page-cache read-ahead: btrfs installs its own bdi with ra_pages = 4096 KB.
Measured rather than assumed -- cold miss_pct vs stride, 1 reader, depth 1, 3 repeats:

    stride       16 KB (= size, "sweep")   0.4 / 0.8 / 0.4 %   <-- the doc's failure mode
    stride       64 KB                    90.6 / 91.0 / 91.0 %
    stride      128 KB                    95.7 / 95.7 / 95.7 %
    stride      256 KB                    97.7 / 98.0 / 98.0 %
    stride      512 KB                    98.8 / 99.2 / 99.2 %
    stride     1024 KB                    99.2 / 99.6 / 99.6 %
    stride     2048 KB                    99.6 / 99.6 / 99.6 %   <-- plateau starts
    stride  3-32   MB                     99.6 % flat

Chose --stride 8388608 (8 MiB) = 2x the btrfs bdi window, on the plateau. The doc's
default 4194304 sits exactly *at* the 4096 KB window, which the doc's own rule ("must
exceed") forbids; it happens to land on the plateau here anyway.
All 264 cold cells verified 0.0000% resident.

--- fixture deviation, and why it was required ---
btrfs is mounted compress=zstd:1 and gen_live_cell_fixture.sh writes a constant byte
(0xAB). Measured: a 1 GiB constant-byte file consumes 32 MB on disk (32:1). du/stat both
report the uncompressed size, so this does not show up in the obvious check. An 8 GB
fixture would have occupied ~250 MB, fit entirely in cache, and turned every "cold miss"
into a zstd decompression rather than a disk read.
Fix: `btrfs property set lab/fixtures/frames_250k_deep compression none` before generating.
Verified: 22 extents for 8 GB (compressed btrfs extents cap at 128 KiB, which would need
~61,000), and free-space delta matches the apparent size.

--- what could NOT be run here, and why ---
RLIMIT_MEMLOCK is 8192 KB, hard, and there is no root on this host. The lab ring arms
(`uring`, `hybrid_lazyring`) call register_buffers for readers x depth x 16 KiB, so they
are capped at readers x depth <= 256:

    r256 d1  = 4096 KiB regbuf   ok
    r128 d2  = 4096 KiB regbuf   ok
    r256 d2  = 8192 KiB regbuf   FAIL 0/3 attempts (ENOMEM), even with memory free
    r256 d4  = 16384 KiB regbuf  FAIL 0/3 attempts

So the doc's grid is complete except (readers=256, depth=2) and (readers=256, depth=4)
for the two ring arms. Those two cells carry `pool` and `product` only, under the label
`scale_nonring_r256` so they cannot be mistaken for cross-arm cells. Filter them out with
`grep -v scale_nonring_r256` before running pair_arms.
`product` is NOT capped: the shipped ReadCtx registers no buffers, and on a kernel refusal
it falls back to the pool rather than failing the ask.
