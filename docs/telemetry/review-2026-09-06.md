## 2 · What the pipeline does when driven — observed on this tree

Five runs, shared stream mode, localhost. A and B are the harness's own cells via the harness page;
C and D drive the same telemetry bundle from a scratch page that asks a trace (one `RequestFrame`
per step, `D` in flight) or one fill, and touches every 4 KiB of each codestream. E is C with
`session.close()` at the end.

| Run | Cell · fixture | Rows | Usable | Client says | Server report |
| --- | --- | --- | --- | --- | --- |
| **A** | on-demand · smoke (3 × 19 B) | 1 | **0** | all headlines and distributions `null`, `valid: true` | 30 s after page close |
| **B** | fill · smoke | 3 | 2 | `ask_to_first == ask_to_last == 840 µs`, `transfer: null` (single read), `marks_after_close: 3` | 30 s |
| **C** | on-demand `D = 1` · 80 × 250 KB | 80 | 79 | `serve_plus_path` p50 0.83 ms · `transfer` p50 1.22 ms (7 reads/frame) · `deliver` p50 180 µs, p95 425 µs · `queue` p50 30 µs · binding: transfer 67, serve 12 · `long_tasks: 0` · clock 5 µs, isolated | 30 s |
| **D** | fill · 80 × 250 KB | 80 | 79 | `serve_plus_path` grows to 143 ms (shared T0, plan §6.1) · `queue` = 775 µs on every row · `deliver: null`, `marks_after_close: 80` · server `send_us` p95 13.8 ms, max 22 ms (flow-control backpressure) | 30 s |
| **E** | C + `session.close()` · smoke, 30 asks | 30 | 29 | as C | **20 ms** after run end |

Three things in that table are new information, not confirmations:

1. **`deliver` is measurable on the TS arm.** The plan expected 10–50 µs, "at or below the clock
   floor". Observed p50 180 µs, p95 425 µs against a 5 µs clock: `ByteAccumulator.take` (one
   250 KB copy), waiter resolution and the microtask hops are forty clock ticks, not one. The
   WASM arm's second copy has room to show here. This weakens the old licence's "never on its own"
   for `deliver` — it is a per-row number, subject to the §3 F3 windowing.
2. **The first-ask row is a different regime.** Run C: frame 0 `serve_plus_path` 4555 µs against a
   p50 of 830, and it arrived in one read. Excluding it is right; excluding *frame 0* is the wrong
   key (F4).
3. **Fill discards a stage it has.** Every preload row closes at `last_byte`, then the harness's
   `waitExactFrame` marks `delivered`, which the tap counts as a mark after close and drops:
   `deliver: null`, `marks_after_close: 80`. The README had to special-case that counter ("does not
   void alone") because of this. The stamp exists and is thrown away (F5).

## 3 · Findings, ranked

### F1 · No cells — N6 cannot run on this harness

`client-runtime-experiment-plan.md` §3 says N6 "is no longer blocked on client wire or telemetry
plumbing". It is still blocked on the shell: no trace is driven, `D` is not held, and the bytes are
not used. Runs A and B are what `verify_e2e.py --telemetry` produces today: a well-formed report about
nothing. Run C shows the same bundle producing 79 valid rows when a forty-line page drives it.

### F2 · The server half of every harvest is lost

Observed in runs A–D: `control read ended` fires 30.3–30.5 s after `page.close()`. Headless Chromium
does not close the WebTransport session on page close; the server sees the QUIC idle timeout. The
session loop then ends, `Tap` drops, the sink flushes. `verify_e2e.py` waits 5 s for the file, sends
SIGTERM (the server has no handler; `sink.rs` flushes only from `Tap::drop`), waits 3 s more, prints
`WARN: missing telemetry-server.json`, and **continues to the next repeat**. On this Chromium the
two-file contract has never been met by the script as written.

Run E proves the fix: `session.close()` from the page before harvest → `control read ended` within
20 ms → report present before `page.close()`. Two lines, one in the harness page, one in the driver's
wait. A SIGTERM handler is the belt to that brace.

### F3 · `long_tasks` is page-lifetime and structurally voids the WASM arm

`clock.ts` 48: the observer is `buffered: true` and unwindowed, so it counts WASM compile and
instantiate. The README voids a run whose `long_tasks` differs materially between arms; the WASM arm
will differ every time for a reason unrelated to the receive path. Every row carries `stall: null`
(`rows.ts` 142) with no site, while the observer already has `startTime` / `duration` per entry —
overlap with a row's open window is exactly the evidence that the row's stamps are late.

### F4 · Frame 0 is excluded by index, not by ask order

`report.ts` 104: `usable = frames.filter(f => f.frame_index !== 0)`. Run C shows the first-ask
regime is real (×5 on `serve_plus_path`). A trace starting at frame 40 keeps its warm-up row and drops
a mid-run frame 0. Module fetch and compile are already isolated into `connect_ms` (12.6–15.8 ms in
every run); what lands on the first row is server cold-page cost and first-stream setup.

### F5 · Fill throws away `delivered`; fill `queue` is one number replicated

Run D: `deliver: null` with 80 discarded marks; `queue` is 775 µs on all 79 usable rows because they
share one gesture and one ask stamp, so its "distribution" is a constant and its p95 is meaningless.

### F6 · Refusals are invisible; a void run cannot be diagnosed

`proxy.ts` 105–128: `proxyBidi` intercepts `writable` only. `FrameError` on the control readable never
reaches the tap, so a refused frame leaves a row open forever. `verify_e2e.py` now fails the run on
`rows_opened != rows_closed` (good), but the report cannot say which row or why. Rows have no
`outcome`; the server row has `locate_outcome` / `write_outcome` and the client has nothing to pair.

### F7 · The two files cannot actually be paired offline

The "no join product" rule rests on the files being alignable by hand. Server rows carry `frame_index`
and `ask_ordinal` but no timestamp; the summary keys observed are exactly `frame_count, integrity,
locate_us, prepare_us, send_us, serve_us, server_bytes_sent, totals` — no `stream_mode`, `study` or
`frame_count` of the fixture. Run D's server `send_us` tail (backpressure) is the batch-queueing
signal the plan wanted isolated, and there is no `batch_position` to read it against.

### F8 · Copy evidence is a declared constant

`copies.copies_per_frame` is typed into the harness. It happens to be right (source read: TS copies
once in `ByteAccumulator.take`; WASM copies chunk → `RecvBuf` then `RecvBuf` → JS heap), but the report
presents it as measured. The experiment plan §5 asks for "transient allocation per frame"; nothing
samples it.

### F9 · Client `ring_capacity: 4096` describes a ring that does not exist

`report.ts` 13 and 169. Client rows are an unbounded array; the server has a real ring.

### F10 · Small stamp-fidelity leaks

- `tap.ts` 76–78: the FoD chunk is decoded and `JSON.parse`d **before** the `ask` stamp is taken.
- `tap.ts` 82: row kind is `frames.length > 1`; a `request_frames` carrying one index is classified
  as an interaction and `ask_granularity` follows it. The op is in the message.
- `ask_flush_us` is captured on every row and exported nowhere; the conflict branch at `tap.ts`
  91–94 is unreachable because `rowsNeedingFlush()` already filters on `ask_flush_us == null`.
- `wrap-session.ts` 38–46: the batch method stamps every frame `delivered` after the last arrives.

### F11 · Three percentile implementations, two rules

`server/src/record/report.rs` and `client/transport-ts/record/percentiles.ts` — nearest-rank.
`lab/window-harness/src/metrics.rs` 277 — `ceil((n−1)·0.95)`. L1 quotes the harness p95; its brief says
L2 owns the fix and shaped runs must wait for it. It is not on this tree.

### F12 · The server cannot start on a host without IPv6

`server.rs` 48 uses wtransport's `with_bind_default`, which is dual-stack `[::]`. This container has
no IPv6 at all (`/proc/sys/net/ipv6` absent) and the server exits with
`Address family not supported by protocol`. There is no `--bind` flag. Every run in §2 needed a
test-only local edit to `InAddrAnyV4`, reverted and not committed. A rig container with the same
kernel config would hit this.

### F13 · The product `timing` object is still degenerate — flag only

`session.ts` 247–249 and `session.rs` 460–462: `chunks: 1`, `firstChunkMs === lastChunkMs`, and both
harness pages print "wire ms" from it. Product call, not this lane's.

## 4 · Decision A — recommendation: A4 as built, close it

| Criterion | A1 + A2 (in tree) | A3 (edit framing helpers) |
| --- | --- | --- |
| Stamp fidelity | `lastByte` at `read()` resolution before any copy; `delivered` at method return. An in-loop stamp would sit in the same event-loop turn — **no fidelity gained** | same |
| Arm parity | one JS patch, same bytes, same arithmetic — parity by construction | two implementations kept identical by review |
| Invasiveness | zero product lines | ~8 sites per client, gated |
| Default-build proof | "never added" | proven inert in two languages |
| Batch correctness | deterministic byte arithmetic; ask identity from the FoD op, not position | same |
| Cost (G5) | **measured: 1 µs per read at 320 frames** (§7) | small, but paid in product code |
| Evidence it works | run C: 79 valid rows, `byte_closure_ok`, 7 reads per frame attributed | — |

A1's only real weakness was the parser cost; it is gone. A2 alone cannot split wire from copy, so it
stays as the `gesture` / `delivered` half of the hybrid. Nothing identified needs a stamp inside
product framing.

**What would reopen it:** a wire change that breaks byte-offset attribution (multi-frame envelopes,
compression), or a stage that can only be stamped inside `session.*`. Neither is on any plan.

**Amend the client ADR:** Decision A → decided (A4 = A1 + A2); record the measured cost; add the one
remaining seam gap — the control readable is not proxied (F6).
