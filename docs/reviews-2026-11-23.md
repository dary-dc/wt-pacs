## 2. The phone round, in plain words

One Android 16 phone (Chrome 157) on home 5 GHz Wi-Fi (at least 568–595 Mbit/s), the evening of 11-22, two DBT
volumes, software decode. Everything here is (M) on that phone unless labelled.

* **The original frame decodes faster than the view.** HTJ2K takes 18.9 ms a frame with three decoders; the AV1 view
  42.1 ms, and a fourth decoder does not help it. So on a fast link the view is no shortcut on this phone.
* **On this link, the original series alone filled first**: 15 of 15 rounds, in a median 0.705 of the view's time.
  The device model had predicted a tie on one volume; it missed. Sending the view, then the whole original series,
  cost no more than the two alone (summed reading 1.031, no difference). One exact frame on request took 216 ms on
  `dbts_b1` (predicted 80–130).
* **Page view against worker view** (cell 3, re-run as PHONE-ROUND-3D): with the page's thread kept busy, the worker
  view dropped 0 of 100 cine frames, the page view a median of 7, in 24 of 24 pairs. Frame changes, the first picture
  and the fill showed no difference. Cell 3's first attempt lost every load's end report: it was 88 KB, over the
  browser's 64 KiB keepalive limit (S: the Fetch standard).
* **The hardware decoder** takes our AV1 but hands back colour: 8 bits exact, 10 bits off by one level (256 × 256
  frames only); 4:0:0 fails.
* **What went wrong, each now a row:** one browser process kept each earlier load's memory (1.0 to 7.6 GB over
  loads 22–28); at load 96 the renderer died with about 7 GB in swap; Chrome once ran old lab code from its cache.
* **Owed:** PHONE-READ-CODE-CHECK, whether the main round's loads all ran the run commit's code. A load it sets apart
  changes the numbers above.
