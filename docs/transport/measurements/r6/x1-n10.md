# X1 at n = 10 — the repeats did not separate it, and that is the answer

`HANDOFF.md` §4.5 carried *"More repeats on X1 (n = 10). Variance is what stopped it
separating. Pure machine time."* It was run. **X1 is still a tie**, and the reason is now
quantified rather than assumed.

Data: [`x1n10.tsv`](x1n10.tsv) — 30 rows, **0 VOID**, arms interleaved within each repeat.

```bash
EXP=x1n10 CELLS="X1" lab/transport/scripts/r6_campaign.sh 10
python3 lab/transport/scripts/r6_analyse.py .local/measurements/r6/x1n10.tsv
```

## The pre-registered verdict: unchanged

| arm | n | min | max | median | vs shared |
| --- | --- | --- | --- | --- | --- |
| shared | 10 | 152.6 | 776.2 | **565.2 ms** | — |
| per-frame + FIFO | 10 | 164.3 | 802.7 | 581.7 ms | +2.9 % — **ranges overlap, NOT a result** |
| per-frame + fair | 10 | 301.6 | 777.7 | 599.1 ms | +6.0 % — **ranges overlap, NOT a result** |

Identical in kind to n = 3. Tripling the repeats moved nothing, because the obstacle was
never the number of repeats:

**`shared`'s own spread across loss realisations is 5.09×** — 152.6 ms to 776.2 ms, the same
arm on the same rig at the same operating point — against a median arm difference of
**4.1 %**. The min/max non-overlap rule cannot resolve a 4 % effect inside a 5× band at any
n. That is a property of the cell, not of the sample size.

## The paired view — reported, deliberately not promoted

Arms are interleaved within each repeat, so the loss realisation is common-mode within a
comparison and the runs are genuinely paired. On that basis:

| | |
| --- | --- |
| shared better in | **8 of 10** paired repeats |
| paired delta (per-frame FIFO − shared) | **+8.8 %**, sd 13.2 % |
| per-repeat range | −10.8 % … +36.7 % |
| sign test | two-sided **p = 0.109** |
| n for 80 % power at this effect | **≈ 18** paired repeats |
| smallest effect n = 10 could detect | 11.7 % |

**This is not a result either, and switching to it now would be the project's own recorded
failure mode.** The pre-registered statistic is min/max non-overlap. Adopting a more
powerful test *after* seeing that the blunt one returned a tie is precisely
*"Phase C retuned the admission rule until the workload passed"* (`HANDOFF.md` §5). It is
reported because hiding a p = 0.109 is its own kind of dishonesty, and refused as evidence
because of when it was chosen.

## Recommendation: stop working on X1

**Resolving it would not change a decision.** §2 of
[`../../transport-conclusions.md`](../../transport-conclusions.md) already concludes that at
low loss the stream shape does not matter and at high loss it does, and X3 carries that with
a **+220 %** paired effect at n = 3 — twenty-five times X1's. An 8.8 % difference at 0.1 %
loss moves no recommendation, no default, and no deployment.

If someone does want it settled, the honest route is to **pre-register the paired test and
n ≈ 18 before running**, not to re-read this data with a better statistic. That is roughly
another hour of machine time for a number that changes nothing, which is why it is not
recommended.

**§4.5's X1 item is closed.** The answer to "would more repeats separate it?" is *no, and
here is the arithmetic showing why the question was the wrong one.*
